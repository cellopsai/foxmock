How to Mock gRPC Services in IntelliJ Without Spinning Up a Server

Testing a feature that depends on a gRPC service you don't own is painful. You either call the real service (needs VPN, can't simulate errors), write a hand-rolled stub (boilerplate per method), or run a Docker container just to get a fake response.

FoxMock is a free IntelliJ IDEA plugin that runs a real gRPC mock server inside the IDE — no extra processes, no config files, no containers. Load your .proto file, set a JSON response for each method, and your app talks to the mock as if it were the real service.

Installation

  1. Open IntelliJ IDEA
  2. Go to File → Settings → Plugins (macOS: IntelliJ IDEA → Settings → Plugins)
  3. Open the Marketplace tab and search for FoxMock
  4. Click Install, then restart the IDE

Or install directly from the JetBrains Marketplace:

Opening the gRPC Panel

After the IDE restarts, click the FoxMock tab in the bottom tool window (or View → Tool Windows → FoxMock) and select the gRPC tab.

screenshot-placeholder-02-grpc-panel.png

FoxMock tool window open on the gRPC tab — empty Proto Files and Methods tables

Step 1 — Load your .proto file

FoxMock needs the .proto file to discover your service structure.

Drag-and-drop the .proto file onto the Proto Files table, or click Load Proto File and browse to it.

screenshot-placeholder-03-drag-drop.png

.proto file dragged onto the Proto Files table

After loading you will see:

  • Proto Files table — one row per loaded file, with service count, method count, and status
  • Methods table — one row per RPC method, pre-filled with a generated sample JSON response
screenshot-placeholder-04-after-load.png

Proto Files and Methods tables filled after loading UserService.proto

You can load multiple .proto files if your services are spread across several files.

Step 2 — Start the mock server

Click Start Server. The status label changes to Status: Running — port 9090.

screenshot-placeholder-05-running.png

gRPC panel showing green "Status: Running — port 9090" label

The default port is 9090. Change it any time in Settings → Tools → FoxMock → gRPC Port — the server restarts automatically.

Step 3 — Configure a method response

Double-click any row in the Methods table (or right-click → Configure…) to open the scenario editor.

screenshot-placeholder-06-configure-dialog.png

Configure dialog for GetUser method — scenario list on the left, editor on the right

The editor has two panels.

Left — scenario list
All scenarios defined for this method. The active one (served to clients) is marked ●.

Right — scenario editor

  • Name — a label for this scenario (e.g. success, not_found)
  • Enabled — uncheck to exclude this scenario from serving entirely
  • Status — gRPC status code: OK, NOT_FOUND, INTERNAL, etc.
  • Message — optional text sent alongside a non-OK status
  • Delay — artificial latency in milliseconds to simulate a slow service
  • Response tab — the JSON body returned to the caller
  • Conditions tab — request-matching rules for automatic scenario switching (covered below)

Edit the JSON in the Response tab, or click ⚙ Generate from Proto to regenerate a sample from the proto message definition. Click Save when done.

screenshot-placeholder-07-response-tab.png

Response tab with JSON editor and "⚙ Generate from Proto" button highlighted

Scenario Management

Why multiple scenarios?

A scenario is a named mock response for one gRPC method. Having several lets you switch what the server returns with one click — no code change, no restart.

A typical set for a user lookup method:

  • success → status OK, full user object
  • not_found → status NOT_FOUND, empty body, message "User does not exist"
  • server_error → status INTERNAL
  • slow_response → status OK, full user object, delay 3 000 ms

Adding a scenario

  1. Open the Configure dialog for the method
  2. Click Add in the scenario list
  3. Type a name and press Enter
  4. Fill in the fields and click Save
screenshot-placeholder-08-multiple-scenarios.png

Configure dialog with four scenarios — success ●, not_found, server_error, slow_response

Switching the active scenario

Select a scenario in the list and click Set Active. The ● badge moves instantly — the very next gRPC call gets that response.

You can also switch without opening the Configure dialog: right-click a method row → Switch Scenario → pick from the submenu.

screenshot-placeholder-09-switch-scenario.png

Methods table right-click menu with Switch Scenario submenu open

Conditional Scenarios — Auto-Switch by Request Content

Manual switching is great for exploratory testing. For automated tests you often want the mock to return different responses based on what the request contains. That's what conditional scenarios are for.

How it works — three-tier resolution

Every incoming call goes through this logic in order:

Tier 1 — Conditional scenarios
Evaluated in priority order (0 = highest). The first scenario whose conditions all match wins.

Tier 2 — Manually active scenario (●)
If no conditional scenario matched, the scenario you last set active is served.

Tier 3 — First enabled scenario
Safety net: if the active scenario is disabled, the first enabled one in the list is used.

Setting up a condition

  1. Open the Configure dialog for a method
  2. Select or add a scenario (e.g. admin_response)
  3. Click the Conditions tab
  4. Click Add Condition
  5. Fill in the row — for example:
    • Type: Body JSONPath
    • Key / Path: $.role
    • Operator: Equals
    • Value: ADMIN
  6. Click Save
screenshot-placeholder-10-conditions-tab.png

Conditions tab — one row: Body JSONPath / $.role / Equals / ADMIN

Now every request whose JSON body has "role": "ADMIN" automatically gets admin_response. Any other role still gets the Tier 2 active scenario — no code change required.

Condition types

  • Body JSONPath — extracts a value from the JSON-transcoded request using a JSONPath expression such as $.user.id
  • Body Regex — tests the whole request body against a regular expression
  • Body Exact — the entire request body must equal the given string

Operators

  • Equals — exact match
  • Contains — substring present
  • Matches (regex) — full regex match
  • Exists — the path must exist (value is ignored)

All conditions on one scenario use AND logic — every condition must pass. Use the Priority spinner to control which conditional scenario wins when multiple could match.

The ⚡ badge

Scenarios that have at least one condition show a ⚡ badge in the list. A scenario that is both conditional and the active fallback shows ⚡●.

screenshot-placeholder-11-badges.png

Scenario list — admin_response with ⚡ badge, success with ● badge

Disabling a Scenario

To temporarily remove a scenario from consideration without deleting it:

  1. Select it in the Configure dialog
  2. Uncheck Enabled
  3. Click Save

The scenario turns gray and italic in the list. FoxMock skips it completely — conditions are not evaluated and it is never used as the Tier 2 fallback. Re-enable it by ticking the checkbox again.

screenshot-placeholder-12-disabled.png

Scenario list with "server_error" grayed-out and italic — Enabled checkbox unchecked

Generating Responses with AI

If your proto messages have many fields, typing realistic JSON by hand is tedious.

⚙ Generate from Proto — click this in the Response tab. FoxMock reads the proto message definition and produces a sample with realistic-looking values: email fields get an email address, id fields get a UUID-style string, price fields get a decimal, and so on.

🤖 Generate with AI — if you have configured an AI provider in Settings → Tools → FoxMock → AI Provider (OpenAI, Claude, Ollama, or a local CLI), this button sends the proto field definitions to the AI and streams the result into the editor. A console window shows the output as it arrives.

Saving and Loading Configuration

Scenarios persist between IDE sessions — save them to a file and restore them any time.

Save

Click Save Config in the gRPC panel. FoxMock writes a .foxmock-grpc JSON file containing every service, method, scenario, condition, and priority.

screenshot-placeholder-14-save-dialog.png

Save Config dialog with filename "grpc-config.foxmock-grpc"

Here is what the file looks like:

{
  "name": "gRPC Config",
  "version": "1.0",
  "services": [{
    "serviceName": "com.example.UserService",
    "methods": [{
      "methodName": "GetUser",
      "activeScenario": "success",
      "scenarios": [
        {
          "name": "success",
          "enabled": true,
          "statusCode": "OK",
          "delayMs": 0,
          "responseJson": "{ \"id\": \"user-123\", \"name\": \"Alice\" }",
          "matchConditions": [],
          "priority": 0
        },
        {
          "name": "not_found",
          "enabled": true,
          "statusCode": "NOT_FOUND",
          "statusMessage": "User does not exist",
          "delayMs": 0,
          "responseJson": "{}",
          "matchConditions": [],
          "priority": 0
        }
      ]
    }]
  }]
}

Load

  1. Load your .proto file first (the server needs the message definitions)
  2. Click Load Config
  3. Select the .foxmock-grpc file

All scenarios are restored. If a method in the file is not found in the loaded proto, it is skipped and listed in the confirmation dialog.

screenshot-placeholder-15-load-dialog.png

Config Loaded dialog — "3 method(s) restored."

Commit the .foxmock-grpc file alongside your .proto files in version control so your whole team can load the same mock setup in two clicks.

Pointing your App at the Mock

The server listens on localhost:9090 by default. Use the insecure/plaintext variant of your client channel — the mock does not use TLS.

ManagedChannel channel = ManagedChannelBuilder
    .forAddress("localhost", 9090)
    .usePlaintext()
    .build();
conn, _ := grpc.Dial("localhost:9090", grpc.WithInsecure())
channel = grpc.insecure_channel("localhost:9090")
const client = new UserServiceClient(
  "localhost:9090",
  grpc.credentials.createInsecure()
);

Transaction Log

Every call is logged in the Transaction Log pane at the bottom of the gRPC panel. Each entry shows the service name, method name, duration in milliseconds, and whether it succeeded or returned an error status. Use it to confirm your app is hitting the mock and to see which scenario was matched.

screenshot-placeholder-16-transaction-log.png

Transaction Log with three rows — GetUser OK 12ms, GetUser NOT_FOUND 8ms, ListUsers OK 45ms

Troubleshooting

Connection refused — confirm the port in FoxMock matches your client's target port (Settings → Tools → FoxMock → gRPC Port) and that the status label says Running.

UNIMPLEMENTED — the method your client is calling is not in any loaded .proto file. Load the correct proto.

Wrong response — make sure you clicked Save after editing. Check the Transaction Log to see which scenario was actually resolved. Make sure the scenario you expect is active (● badge) or that its conditions matched.

Proto fails to load — FoxMock parses proto3. If your proto imports other files, those files must be on disk in a path relative to the loaded file.
