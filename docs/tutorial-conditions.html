Condition Types & Operators — Smart Scenario Routing in FoxMock

Conditions are what turn a mock from a static response machine into something intelligent. Without conditions, you manually flip the active scenario every time the test changes. With conditions, FoxMock reads the incoming request — its body, query parameters, or headers — and automatically serves the right scenario.

This tutorial is a complete, practical guide to every condition type FoxMock supports, every operator you can use, and how to combine them for precise automatic routing.

How conditions work

Every route in FoxMock can have multiple scenarios. Only one scenario is served for any given request. Conditions let you configure exactly which scenario wins automatically, based on what is in the request.

When a request arrives, FoxMock runs through a three-tier resolution process:

1
Conditional scenarios (⚡) — evaluated in priority order (lowest number first). FoxMock checks each condition on a scenario. If all conditions pass, that scenario wins and is served immediately. Subsequent scenarios are not evaluated.
2
Manually active scenario (●) — if no conditional scenario matched, the scenario you last activated manually via Set Active is served. This is your default happy path.
3
First enabled scenario — safety net. If the active scenario is disabled or unset, FoxMock falls back to the first enabled scenario so you never get an unexpected 404.

Conditions only matter at Tier 1. A scenario without any conditions never participates in Tier 1 — it can only win at Tier 2 or 3. A scenario with at least one condition shows a ⚡ badge in the list.

The five condition types

TypeWhat it inspectsWorks on
Body JSONPath A specific field inside the JSON request body, addressed by a JSONPath expression REST, gRPC
Body Regex The entire raw request body matched against a regular expression REST, gRPC
Body Exact The entire raw request body must equal the condition value exactly REST, gRPC
Query Param A URL query parameter value (e.g. ?page=2) REST only
Header A request header value (e.g. Authorization, X-Tenant-Id) REST only

Query Param and Header conditions are only available for REST (HTTP) routes because gRPC does not use URL query strings or HTTP headers in the same way. See the gRPC section for details.

The four operators

Once FoxMock extracts a value (the field, param, or header), it applies an operator to decide whether the condition passes.

OperatorPasses when…Example
Equals Extracted value is exactly equal to the condition value (case-sensitive) $.status Equals active
Contains Extracted value contains the condition value as a substring Header Authorization Contains expired
Matches (regex) Extracted value fully matches the regular expression in the condition value $.quantity Matches [1-9][0-9]*
Exists The field, parameter, or header is present (has any value). The condition value field is ignored. Query Param debug Exists
Case sensitivity: Equals and Contains are case-sensitive. Use Matches (regex) with the (?i) prefix for case-insensitive matching — for example (?i)sku-out matches SKU-OUT, sku-out, and Sku-Out.

Body JSONPath — match a specific field

JSONPath is the most targeted condition type for JSON bodies. It lets you read exactly one field from the request payload, no matter how deeply nested, and apply an operator to its value.

JSONPath quick reference

ExpressionReadsExample payload
$.action Top-level field {"action": "cancel"}
$.user.role Nested field {"user": {"role": "admin"}}
$.items[0].sku First array element {"items": [{"sku": "A1"}]}
$.items.length() Array length {"items": [{}, {}, {}]} → 3
$.meta.priority Deeply nested value {"meta": {"priority": "high"}}

Example: POST /api/orders — route by action field

Suppose your order endpoint handles three operations distinguished by an action field in the POST body:

POST /api/orders
{"action": "create",  "productId": "SKU-001", "quantity": 2}
{"action": "cancel",  "orderId": "ORD-8821"}
{"action": "reorder", "orderId": "ORD-8821"}

Create a route for POST /api/orders with three scenarios. For each scenario, open the Conditions tab and add one condition:

ScenarioTypeKey / PathOperatorValue
order_created Body JSONPath $.action Equals create
order_cancelled Body JSONPath $.action Equals cancel
order_reordered Body JSONPath $.action Equals reorder

Test it:

# Triggers order_cancelled
curl -s -X POST "http://localhost:8089/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"action": "cancel", "orderId": "ORD-8821"}'
# → 200 {"message": "Order ORD-8821 cancelled"}

# Triggers order_created
curl -s -X POST "http://localhost:8089/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"action": "create", "productId": "SKU-001", "quantity": 2}'
# → 201 {"orderId": "ORD-9902", "status": "confirmed"}

Using Matches (regex) with JSONPath

JSONPath + Matches (regex) is powerful when the field value itself needs pattern matching. Example — flag any order with a priority code that starts with URGENT-:

TypeKey / PathOperatorValue
Body JSONPath $.priority Matches (regex) URGENT-.* 
# Triggers the "urgent_order" scenario
curl -s -X POST "http://localhost:8089/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"action": "create", "priority": "URGENT-001", "productId": "SKU-999"}'

Using Exists with JSONPath

Use Exists to check whether a field is present at all, without caring about its value. Useful for feature-flag fields, optional parameters, or discriminating between two payload shapes:

ScenarioTypeKey / PathOperator
bulk_order Body JSONPath $.items Exists
single_order Body JSONPath $.productId Exists

A body with "items": [...] triggers bulk_order. A body with "productId": "..." (and no items) triggers single_order. Give bulk_order a lower priority number so it is checked first.

Body Regex — flexible pattern matching

Body Regex runs a single regular expression against the entire raw body string. It is the right choice when:

  • The body is not JSON (plain text, XML, form-encoded)
  • You want to check if a certain string appears anywhere in the body
  • You need to match multiple conditions in one expression
  • You want to match the absence of a field

The operator for Body Regex is almost always Matches (regex). The expression must match the entire body (FoxMock uses Java's Pattern.matches() which anchors the pattern), so use .* around the part you care about.

Example: detect missing required field

Return a 422 when productId is missing from the body:

ScenarioTypeOperatorValue (regex)
missing_product Body Regex Matches (regex) ^(?!.*"productId")[\s\S]*$

The negative lookahead (?!.*"productId") makes the pattern match any body that does not contain the string "productId".

# No productId field → triggers missing_product (422)
curl -s -X POST "http://localhost:8089/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"quantity": 5}'
# → 422 {"error": "Validation failed", "fields": {"productId": "required"}}

Example: match a specific value anywhere in the body

Trigger an out_of_stock scenario whenever the body contains SKU-OUT anywhere — regardless of which field it's in:

ScenarioTypeOperatorValue (regex)
out_of_stock Body Regex Matches (regex) .*SKU-OUT.*

Example: match plain-text or XML bodies

For non-JSON bodies, Body Regex is the only body condition type that works reliably. Example — trigger a specific scenario when a SOAP body contains <CancelOrder>:

ScenarioTypeOperatorValue (regex)
cancel_soap Body Regex Matches (regex) [\s\S]*<CancelOrder>[\s\S]*
Tip — multiline bodies: Use [\s\S]* instead of .* when the body spans multiple lines, because . does not match newlines by default in Java regex.

Body Exact — fixed payload matching

Body Exact is the simplest type: FoxMock compares the entire raw request body against your condition value character for character. Whitespace counts. {"a":1} and { "a": 1 } are different.

It is most useful in unit tests where the same serializer always produces the same output, and you want the tightest possible match with zero ambiguity.

Example: ping / health check

# Your health-check service always sends exactly this
curl -s -X POST "http://localhost:8089/api/ping" \
  -H "Content-Type: application/json" \
  -d '{"type":"ping"}'
ScenarioTypeOperatorValue
pong Body Exact Equals {"type":"ping"}

Any variation in spacing, field order, or encoding will not match. For flexibility, use Body JSONPath instead.

Query Param conditions — GET routing by URL

Query Param conditions read values from the URL query string. They are ideal for GET endpoints where there is no request body, and the response depends on parameters like status, page, version, or userId.

Example: GET /api/orders — route by status filter

Create a route for GET /api/orders with three scenarios:

ScenarioTypeKey (param name)OperatorValue
pending_orders Query Param status Equals pending
completed_orders Query Param status Equals completed
all_orders (active ●) — — — — 
# Triggers pending_orders
curl -s "http://localhost:8089/api/orders?status=pending"
# → [{"orderId":"ORD-001","status":"pending"}, ...]

# Triggers completed_orders
curl -s "http://localhost:8089/api/orders?status=completed"
# → [{"orderId":"ORD-800","status":"completed"}, ...]

# No matching condition → falls back to all_orders (active ●)
curl -s "http://localhost:8089/api/orders"
# → [all orders list]

Example: pagination — route by page number range

Return an empty page when the caller requests a page beyond the data set:

ScenarioTypeKeyOperatorValue
empty_page Query Param page Matches (regex) [5-9]|[1-9][0-9]+

The regex [5-9]|[1-9][0-9]+ matches any single digit 5–9 or any number with two or more digits (10+). Pages 1–4 fall through to the active scenario.

curl -s "http://localhost:8089/api/orders?page=7"
# → {"items": [], "page": 7, "total": 0}

curl -s "http://localhost:8089/api/orders?page=2"
# → {"items": [...], "page": 2, "total": 42}

Example: check a parameter exists at all

Return a debug response when the debug param is present, regardless of its value:

ScenarioTypeKeyOperator
debug_response Query Param debug Exists 
curl -s "http://localhost:8089/api/orders?debug=true"
curl -s "http://localhost:8089/api/orders?debug=1"
curl -s "http://localhost:8089/api/orders?debug"
# All three trigger debug_response

Header conditions — auth, tenant, version

Header conditions inspect request headers. This is how you simulate authentication failures, multi-tenant routing, API versioning, and feature flags — all based on what the caller sends in the header, not the body.

Example: simulate an expired token

# Invalid token → triggers unauthorized scenario
curl -s -X POST "http://localhost:8089/api/orders" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer expired_abc123" \
  -d '{"productId": "SKU-001", "quantity": 2}'
# → 401 {"error": "Unauthorized"}
ScenarioTypeKey (header name)OperatorValue
unauthorized Header Authorization Contains expired

Any request carrying a token that contains the word expired gets a 401 — the body is never inspected.

Example: multi-tenant routing by X-Tenant-Id

ScenarioTypeKeyOperatorValue
tenant_acme Header X-Tenant-Id Equals acme
tenant_globex Header X-Tenant-Id Equals globex 
curl -s "http://localhost:8089/api/config" -H "X-Tenant-Id: acme"
# → {"theme": "blue", "plan": "enterprise"}

curl -s "http://localhost:8089/api/config" -H "X-Tenant-Id: globex"
# → {"theme": "green", "plan": "starter"}

Example: API versioning by Accept header

ScenarioTypeKeyOperatorValue
v2_response Header Accept Contains application/vnd.api.v2
v1_response (active ●) — — — — 
curl -s "http://localhost:8089/api/users/1" \
  -H "Accept: application/vnd.api.v2+json"
# → v2 response shape

curl -s "http://localhost:8089/api/users/1"
# → v1 response shape (active fallback)

Multiple conditions on one scenario (AND logic)

You can add as many conditions as you like to a single scenario. FoxMock requires all of them to pass — it is pure AND logic. If any condition fails, the scenario is skipped and FoxMock moves on to the next one by priority.

This lets you build precise conditions that would be too broad with a single check.

Example: out-of-stock only for large quantities of a specific SKU

Condition #TypeKey / PathOperatorValue
1 Body JSONPath $.productId Equals SKU-LIMITED
2 Body JSONPath $.quantity Matches (regex) [5-9]|[1-9][0-9]+ 
# Both conditions pass (SKU-LIMITED + quantity ≥ 5) → out_of_stock
curl -s -X POST "http://localhost:8089/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"productId": "SKU-LIMITED", "quantity": 10}'
# → 409 {"error": "Out of stock"}

# Only condition 1 passes (quantity = 2 < 5) → no match, falls through
curl -s -X POST "http://localhost:8089/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"productId": "SKU-LIMITED", "quantity": 2}'
# → 201 {"orderId": "ORD-9903", ...} (active fallback)

Example: combine body and header conditions

Conditions can mix types freely. Trigger a rate-limit scenario only when a specific client header is present and the order quantity is high:

Condition #TypeKey / PathOperatorValue
1 Header X-Client-Id Equals test-client-overload
2 Body JSONPath $.quantity Matches (regex) [1-9][0-9]{2,}

Both must be true for the rate-limit scenario to fire. A normal client sending a large quantity, or the test client sending a small quantity, both pass through to other scenarios.

Priority between scenarios

When multiple conditional scenarios could both match the same request, the Priority field controls which one is evaluated first. Lower number = evaluated first = wins if it matches.

Set priority in the Configure dialog: select a scenario and adjust the Priority spinner.

A recommended priority ordering for a POST endpoint with auth, validation, and business conditions:

PriorityScenarioRationale
0 unauthorized Auth check before anything else — a bad token should never hit business logic
1 missing_product_id Input validation runs before stock checks
2 out_of_stock Stock check only relevant for valid, authenticated requests
— success (active ●) Happy path serves everything that passes Tier 1
Scenarios with equal priority are evaluated in the order they appear in the list. If two scenarios can both match the same request, give the more specific one the lower priority number to ensure it fires first.

Regex in route paths

Conditions match on the contents of a request — body, params, headers. But you can also use regex in the route path itself to match a whole family of URLs with one route.

FoxMock automatically detects whether a path is a regex by looking for regex characters: [, (, \, ^, $, |, or +. If any are present, the path is compiled as a Java regex and matched using matches(). Otherwise it is treated as a template where {param} matches any path segment and * matches anything.

Examples

Path in FoxMockMatchesDoes not match
/api/orders/{id} /api/orders/42, /api/orders/ORD-001 /api/orders/42/items
/api/orders/[0-9]+ /api/orders/42, /api/orders/1000 /api/orders/abc, /api/orders/ORD-001
/api/(orders|products)/[0-9]+ /api/orders/5, /api/products/99 /api/users/5
/api/v[12]/.* /api/v1/orders, /api/v2/users/me /api/v3/orders

Routes with regex paths are shown with a ~ prefix in the route table to make them easy to identify at a glance.

Path regex vs body conditions: Path regex narrows down which route handles a request. Body conditions narrow down which scenario within that route is served. They work at different levels and complement each other perfectly — for example, a regex path /api/orders/[0-9]+ combined with a body condition $.action Equals cancel gives you precise routing with minimal routes.

Conditions in gRPC

FoxMock's gRPC mock also supports conditional scenarios. Because gRPC calls don't have URL query strings or HTTP headers in the traditional sense, only the body-based condition types are available for gRPC routes:

TypeAvailable for gRPC
Body JSONPath Yes — gRPC request messages are serialised as JSON for matching
Body Regex Yes — matched against the JSON representation of the request
Body Exact Yes — matches the entire JSON serialisation of the request message
Query Param No — gRPC does not use URL query parameters
Header No — not supported for gRPC routes

The setup workflow is identical to REST: open the Configure dialog for a method, select a scenario, go to the Conditions tab, and add conditions exactly as you would for a REST route. The same Tier 1 / 2 / 3 resolution logic applies.

For a full gRPC walkthrough including conditional scenarios, see the gRPC Tutorial.

Troubleshooting

Condition set but active fallback is always served
Check that the scenario is Enabled (checkbox in the Configure dialog). Disabled scenarios are invisible to Tier 1 — their conditions are never evaluated. Also confirm the scenario shows a ⚡ badge; if it shows only ●, the conditions were not saved.

JSONPath condition never matches
JSONPath is case-sensitive: $.ProductId does not match a field named productId. Open the Transaction Log and check the B: line — it shows the exact body FoxMock received. Verify the field name, nesting level, and that the body is valid JSON. If the body is form-encoded or plain text, JSONPath silently fails — switch to Body Regex.

Regex condition is not matching when it should
FoxMock uses Pattern.matches() which anchors the pattern to the full string. A pattern like SKU-OUT without surrounding .* will only match a body that is exactly SKU-OUT and nothing else. Add .* around the part you care about: .*SKU-OUT.*. For multiline bodies, use [\s\S]*SKU-OUT[\s\S]*.

Query Param condition not matching
The Key field must be the exact parameter name as it appears in the URL — case-sensitive. Status does not match ?status=pending. Check the Transaction Log for the exact query string FoxMock received.

Header condition not matching
Header names are matched case-insensitively in HTTP, but verify the value. If your token is Bearer valid_token and the condition is Contains expired, it correctly won't match. Check the Transaction Log's H: line for the actual header value.

Wrong scenario wins when two conditions could both match
Check the Priority spinners. The scenario with the lowest number is evaluated first. If two scenarios have the same priority, the one higher in the list wins. Open the Configure dialog and re-order or adjust priorities.

Regex in the route path not working
Make sure the path contains at least one regex character ([, (, \, ^, $, |, +). A plain path like /api/orders/42 is always treated as a literal template, not a regex. The route table shows ~ before the path when auto-detection is active.

That is everything you need to know about conditions in FoxMock. Start with a single Body JSONPath condition on your most common scenario, see the ⚡ badge appear, and test it with curl. From there, layering in multiple conditions and adjusting priorities is straightforward.
