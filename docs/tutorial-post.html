How to Mock POST APIs with Body Matching & Scenarios in IntelliJ

POST endpoints are harder to mock than GET endpoints because the response often depends on what the caller sends, not just the URL. A POST /api/orders should return a 201 when the payload is valid, a 422 when a required field is missing, a 409 when the item is out of stock, and a 503 when the inventory service is down.

FoxMock handles all of this with one route and multiple named scenarios — each triggered automatically by matching against the incoming request body using JSONPath, regex, or exact text. No code change. No server restart. No extra tools outside your IDE.

Installation

  1. Open IntelliJ IDEA
  2. Go to File → Settings → Plugins (macOS: IntelliJ IDEA → Settings → Plugins)
  3. Open the Marketplace tab and search for FoxMock
  4. Click Install, then restart the IDE

Or install directly:

After restarting, open View → Tool Windows → FoxMock and select the HTTP Mock tab.

Request body vs response body

Before building anything it is worth being clear on the two bodies involved in every POST interaction, because they are easy to mix up:

BodyDirectionIn FoxMock
Request body (-d in curl) Your app → FoxMock Read by conditions to decide which scenario wins
Response body FoxMock → your app Set in the Response tab of each scenario

The Response tab in FoxMock's Configure dialog is always the response body — what FoxMock sends back. The request body your app sends is never configured; it is only inspected by conditions to pick the right scenario.

A curl call makes this concrete:

# -d is the REQUEST body — what your app sends to FoxMock
curl -s -X POST "http://localhost:8090/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"productId": "SKU-001", "quantity": 2}'

# FoxMock reads {"productId":"SKU-001","quantity":2},
# evaluates conditions, and returns the matching RESPONSE body
# → {"orderId": "ORD-8821", "status": "confirmed", "total": 59.98}

Add a POST route

We will mock POST /api/orders — a typical order-creation endpoint. Click Start Server first, then click Add Route.

Fill in the route dialog:

  • Method: POST
  • Path: /api/orders

In the Response tab of the default scenario, set Status to 201 and paste this response body:

{
  "orderId": "ORD-8821",
  "status": "confirmed",
  "productId": "SKU-001",
  "quantity": 2,
  "total": 59.98,
  "estimatedDelivery": "2026-05-22"
}

Name this scenario success. Click Save.

Test it — the -d value is the request body your app would send:

curl -s -X POST "http://localhost:8090/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"productId": "SKU-001", "quantity": 2}'

FoxMock returns the 201 response body you configured. At this point FoxMock ignores the request body entirely — it has no conditions yet, so every POST to /api/orders gets the success response.

Create multiple scenarios

Real POST endpoints return different responses depending on what the caller sends. Here is a full set for an order endpoint:

Scenario nameStatusWhen to use
success201Valid payload — order confirmed
validation_error422Required field missing or invalid
out_of_stock409Requested product unavailable
unauthorized401Missing or invalid auth token
server_error500Simulate a backend failure
slow_response2013 000 ms delay — timeout testing

Adding each scenario

Double-click the POST /api/orders row to open the Configure dialog. Click Add Scenario for each entry below.

validation_error — Status 422, body:

{
  "error": "Validation failed",
  "fields": {
    "productId": "productId is required",
    "quantity":  "quantity must be a positive integer"
  }
}

out_of_stock — Status 409, body:

{
  "error": "Conflict",
  "message": "Product SKU-001 is currently out of stock. Try again later."
}

unauthorized — Status 401, add a response header WWW-Authenticate: Bearer realm="api", body:

{
  "error": "Unauthorized",
  "message": "A valid Bearer token is required."
}

server_error — Status 500, body:

{
  "error": "Internal Server Error",
  "message": "The order service is temporarily unavailable."
}

slow_response — Status 201, same body as success, Delay set to 3000 ms. Use this to test how your app handles slow upstream responses or to verify timeout logic.

Switch scenarios manually

The scenario marked ● is the one currently being served. To switch:

From the Configure dialog: select a scenario and click Set Active. The ● badge moves immediately — the very next POST gets that response. No restart required.

Without opening the dialog: right-click the route row → Switch Scenario → pick from the submenu.

Try triggering the validation error manually:

# Set validation_error active, then send any POST body:
curl -s -X POST "http://localhost:8090/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"productId": "SKU-001", "quantity": 2}'
# → 422 {"error":"Validation failed","fields":{...}}

Manual switching is ideal during exploratory testing or demo sessions where you want full control over what the mock returns regardless of the payload.

Conditional matching on the request body

For automated tests you need the mock to return the right response automatically — based on what the caller sends — without any human switching. That is what body conditions are for.

When a POST arrives, FoxMock reads the raw request body and evaluates all conditional scenarios in priority order. The first scenario whose conditions all pass wins.

The three body condition types

TypeHow it worksBest for
Body JSONPath Evaluates a JSONPath expression against the parsed JSON body and applies an operator to the extracted value Matching a specific field like $.status or $.user.role
Body Regex Applies a regular expression to the entire raw body string Flexible matching when the body format varies or isn't strict JSON
Body Exact The entire raw body must equal the condition value exactly (whitespace-sensitive) Fixed payloads in unit tests where the body is always identical

Example: auto-route based on productId

We want:

  • productId = "SKU-OUT" → out_of_stock (409)
  • productId missing → validation_error (422)
  • any other valid payload → success (201, active fallback)

Step 1 — Condition on out_of_stock

  1. Open the Configure dialog for POST /api/orders
  2. Select the out_of_stock scenario
  3. Click the Conditions tab → Add Condition
  4. Fill in:
    • Type: Body JSONPath
    • Key / Path: $.productId
    • Operator: Equals
    • Value: SKU-OUT
  5. Click Save

The scenario now shows a ⚡ badge — it has at least one condition.

screenshot-placeholder-post-03-condition-jsonpath.png

Conditions tab — Body JSONPath / $.productId / Equals / SKU-OUT

Step 2 — Condition on validation_error

  1. Select the validation_error scenario
  2. Click Conditions tab → Add Condition
  3. Fill in:
    • Type: Body JSONPath
    • Key / Path: $.productId
    • Operator: Exists
    • Value: leave blank, then negate it — use operator Matches (regex) with value ^$ on Body Regex if your version doesn't have a "Not Exists" operator. Alternatively use a second condition described in the JSONPath section.

A simpler approach for missing fields is Body Regex:

  • Type: Body Regex
  • Operator: Matches (regex)
  • Value: ^(?!.*"productId").*$

This regex matches any body that does not contain the string "productId" at all.

Step 3 — Test it

# Triggers out_of_stock ($.productId = "SKU-OUT")
curl -s -X POST "http://localhost:8090/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"productId": "SKU-OUT", "quantity": 1}'
# → 409 {"error":"Conflict","message":"Product SKU-001 is currently out of stock..."}

# Triggers validation_error (productId field missing)
curl -s -X POST "http://localhost:8090/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"quantity": 3}'
# → 422 {"error":"Validation failed","fields":{...}}

# Falls through to active fallback → success
curl -s -X POST "http://localhost:8090/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"productId": "SKU-001", "quantity": 2}'
# → 201 {"orderId":"ORD-8821","status":"confirmed",...}

Three different responses from one route, zero manual switching, zero code changes.

JSONPath conditions in depth

JSONPath is the most powerful condition type for POST endpoints because it targets individual fields regardless of how the rest of the body is structured.

Common JSONPath expressions

ExpressionMatchesExample payload
$.action Top-level field {"action": "cancel"}
$.user.role Nested field {"user": {"role": "admin"}}
$.items[0].sku First element in an array {"items": [{"sku": "A1"}]}
$.items.length() Array length (Jayway syntax) {"items": [{}, {}, {}]} → 3
$.metadata.priority Deeply nested value {"metadata": {"priority": "high"}}

Operators for JSONPath

  • Equals — the extracted value must exactly match the condition value (string comparison, case-sensitive)
  • Contains — the extracted value contains the condition value as a substring
  • Matches (regex) — the extracted value matches a regular expression
  • Exists — the JSONPath expression resolves to any value (field must be present); the condition value is ignored

Practical example: order action routing

Suppose your single endpoint handles multiple order actions distinguished by an action field:

POST /api/orders
{"action": "create",  "productId": "SKU-001", "quantity": 2}
{"action": "cancel",  "orderId": "ORD-8821"}
{"action": "reorder", "orderId": "ORD-8821"}

Create three scenarios and assign a JSONPath condition to each:

ScenarioJSONPathOperatorValue
order_created $.action Equals create
order_cancelled $.action Equals cancel
order_reordered $.action Equals reorder

Now each action gets its own realistic response automatically. Test:

curl -s -X POST "http://localhost:8090/api/orders" \
  -H "Content-Type: application/json" \
  -d '{"action": "cancel", "orderId": "ORD-8821"}'
# → the order_cancelled response body immediately

Matching on request headers

POST endpoints usually require authentication. You can use a Header condition to return different responses based on the Authorization header — no body matching needed.

Example: simulate an expired token

  1. Select the unauthorized scenario
  2. Click Conditions tab → Add Condition
  3. Fill in:
    • Type: Header
    • Key / Path: Authorization
    • Operator: Contains
    • Value: expired
  4. Click Save

Now any POST that includes Authorization: Bearer expired_token_here returns a 401 — regardless of what the body contains:

# Triggers unauthorized scenario
curl -s -X POST "http://localhost:8090/api/orders" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer expired_abc123" \
  -d '{"productId": "SKU-001", "quantity": 2}'
# → 401 {"error":"Unauthorized","message":"A valid Bearer token is required."}

# Valid token → falls through to body conditions → success
curl -s -X POST "http://localhost:8090/api/orders" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer valid_token_xyz" \
  -d '{"productId": "SKU-001", "quantity": 2}'
# → 201 {"orderId":"ORD-8821","status":"confirmed",...}

All condition types available for REST routes

TypeWhat it matches onExample key
Query Param A URL query parameter value page, version
Header A request header value Authorization, X-Tenant-Id
Body JSONPath A field inside the JSON request body $.action, $.user.role
Body Regex The entire raw body against a regular expression .*"action":"cancel".*
Body Exact The entire body must equal the value exactly {"action":"ping"}

Priority and multiple conditions

Multiple conditions on one scenario (AND logic)

When you add more than one condition to a scenario, FoxMock requires all of them to pass. This lets you build precise targeting:

Example — trigger out_of_stock only when the product is SKU-OUT and the quantity is more than zero:

TypeKey / PathOperatorValue
Body JSONPath $.productId Equals SKU-OUT
Body JSONPath $.quantity Matches (regex) [1-9][0-9]*

Both conditions must be true for the scenario to win. If either fails, FoxMock continues to the next conditional scenario by priority.

Priority between scenarios

When multiple conditional scenarios could match the same request, the Priority spinner controls which one wins. Lower number = higher priority. A scenario with priority 0 is evaluated before one with priority 1.

A good default ordering for the order endpoint:

PriorityScenarioWhy first
0 unauthorized Auth check should fire before any business logic
1 validation_error Invalid input caught before stock check
2 out_of_stock Stock check only relevant for valid requests
— success (active fallback ●) Serves all requests that pass through Tier 1

To set priority: open the Configure dialog, select a scenario, and adjust the Priority spinner in the config row at the top of the editor.

Three-tier resolution explained

Every POST request goes through this logic in order:

1
Conditional scenarios — evaluated in priority order (lower number first). The first scenario whose all conditions match the incoming request body, headers, and/or query params is served immediately.
2
Manually active scenario (●) — if no conditional scenario matched, the scenario you last set active via Set Active or Switch Scenario is served. This is your default happy path.
3
First enabled scenario — safety net. If the active scenario is disabled or not set, FoxMock falls back to the first enabled scenario in the list so the server never returns a 404 unexpectedly.

Scenario badges reflect where each scenario sits:

  • ● — the active Tier 2 fallback
  • ⚡ — has at least one condition (participates in Tier 1)
  • ⚡● — conditional and also the active fallback
  • gray / italic — disabled, skipped at all three tiers

Applied to the order endpoint

POST /api/orders  {"productId": "SKU-OUT", "quantity": 2}

Tier 1 scan (priority order):
  0 — unauthorized  → Authorization header present, not "expired" → SKIP
  1 — validation_error → body has productId → SKIP
  2 — out_of_stock  → $.productId = "SKU-OUT" → MATCH ✓
→ Serve out_of_stock (409)
POST /api/orders  {"productId": "SKU-001", "quantity": 2}

Tier 1 scan:
  0 — unauthorized  → SKIP
  1 — validation_error → SKIP
  2 — out_of_stock  → $.productId = "SKU-001" ≠ "SKU-OUT" → SKIP
No conditional match → move to Tier 2
→ Serve success ● (201)

Disabling a scenario

To take a scenario out of rotation without deleting it:

  1. Open the Configure dialog
  2. Select the scenario
  3. Uncheck Enabled
  4. Click Save

The scenario turns gray and italic. FoxMock skips it at all three tiers — its conditions are never evaluated and it is never used as the Tier 2 fallback.

This is particularly useful for POST routes:

  • Keep server_error defined but disabled during normal development. Enable it only when testing your error handling or retry logic.
  • Keep slow_response disabled by default. Enable it only when testing loading states or timeout behaviour.
  • Keep unauthorized disabled when working on features that don't involve auth, so it doesn't accidentally intercept valid requests.

Transaction log for POST requests

The Request Log pane at the bottom of the HTTP Mock panel records every request FoxMock receives. For POST requests it shows additional context that is critical for debugging body-condition matching:

  • Timestamp, method, path, status code, and duration
  • Which scenario was matched (in brackets)
  • The decoded request body as indented detail lines
[14:02:11]  POST  /api/orders  →  201  9ms   [success ●]
    ↳ B: {"productId":"SKU-001","quantity":2}

[14:02:28]  POST  /api/orders  →  409  6ms   [out_of_stock ⚡]
    ↳ B: {"productId":"SKU-OUT","quantity":1}

[14:02:45]  POST  /api/orders  →  422  4ms   [validation_error ⚡]
    ↳ B: {"quantity":5}

[14:03:01]  POST  /api/orders  →  401  3ms   [unauthorized ⚡]
    ↳ B: {"productId":"SKU-001","quantity":2}
    ↳ H: Authorization: Bearer expired_abc123

The B: prefix marks the request body. The H: prefix marks a notable request header. If the wrong scenario is being served, check the log first — the scenario name in brackets tells you exactly which tier matched and which scenario won.

Save & load collections

Your entire mock setup — all routes, scenarios, conditions, priorities — can be saved to a .fmcoll.json file and restored at any time.

Save

  1. Click 💾 Save Collection in the HTTP Mock panel toolbar
  2. Choose which routes to include (check POST /api/orders)
  3. Pick a filename such as orders-api.fmcoll.json

The saved file includes every scenario and its conditions:

{
  "name": "Orders API",
  "version": "1.0",
  "routes": [
    {
      "method": "POST",
      "path": "/api/orders",
      "activeScenario": "success",
      "scenarios": [
        {
          "name": "success",
          "enabled": true,
          "statusCode": 201,
          "delayMs": 0,
          "responseBody": "{\"orderId\":\"ORD-8821\",\"status\":\"confirmed\",...}",
          "matchConditions": [],
          "priority": 0
        },
        {
          "name": "out_of_stock",
          "enabled": true,
          "statusCode": 409,
          "delayMs": 0,
          "responseBody": "{\"error\":\"Conflict\",...}",
          "matchConditions": [
            {
              "type": "BODY_JSONPATH",
              "key": "$.productId",
              "operator": "EQUALS",
              "value": "SKU-OUT"
            }
          ],
          "priority": 2
        },
        {
          "name": "server_error",
          "enabled": false,
          "statusCode": 500,
          "delayMs": 0,
          "responseBody": "{\"error\":\"Internal Server Error\",...}",
          "matchConditions": [],
          "priority": 0
        }
      ]
    }
  ]
}

Load

  1. Click 📂 Load Collection
  2. Select the .fmcoll.json file
  3. For each route that already exists, choose Keep, Replace, or Merge scenarios

Commit the .fmcoll.json file to version control. Every developer on the team loads the same POST mock setup in two clicks — with all body conditions and priorities intact.

Troubleshooting

Wrong scenario served — body condition not matching
Open the Transaction Log. The B: line shows exactly what FoxMock received. Compare it with the JSONPath or regex in your condition. JSONPath is case-sensitive: $.ProductId does not match a field named productId. Use Matches (regex) with (?i)sku-out for case-insensitive matching.

Conditions are set but all requests still hit the active fallback
Check that the scenario is Enabled (the checkbox in the Configure dialog). Disabled scenarios are skipped at Tier 1 — their conditions are never evaluated. Also confirm the scenario has a ⚡ badge in the list; if it shows only ● or nothing, conditions were not saved.

404 — FoxMock returns "No mock route configured"
The method must match exactly. A route defined as POST /api/orders will not match a PUT /api/orders request. Also check the path: /api/orders and /api/orders/ (trailing slash) are treated as different paths.

JSONPath expression returns nothing
If the request body is not valid JSON (e.g. form-encoded data, plain text), JSONPath evaluation silently fails and the condition does not match. Check the B: line in the log. If the body is not JSON, switch to Body Regex or Body Exact instead.

The server_error scenario fires unexpectedly
It was probably left enabled. Open the Configure dialog, select it, uncheck Enabled, and save. Disabled scenarios are shown gray and italic and are never served.

Connection refused
The HTTP Mock server is not running. Check the status strip — click Start Server if it shows Stopped. Confirm the port in FoxMock matches the one in your curl command (Settings → Tools → FoxMock → HTTP Port).
